# Internationalisation

Read this before writing any text a user will read, or touching the translation
machinery.

This records how the front-end handles translations today. Where a task would
depart from it, that is a convention change to take deliberately and write down
here.

## The rule

**No user-facing string is written in a component.** Every one comes from a
translation file, through `t()`. That includes text a user never sees directly
but a screen reader or a search engine does: `alt` text, `title`, `aria-label`,
`placeholder`.

```tsx
import { useI18n } from "../../i18n/I18nProvider/context";

function LogInButton() {
  const { t } = useI18n();
  return <Button icon={<FaGoogle />}>{t("authentication.log-in")}</Button>;
}
```

The hook comes from `i18n/I18nProvider/context`, not from the provider file.
`App.tsx` wraps the router in `I18nProvider`, so every component below it can
call `useI18n` without any further setup.

## How it works

The implementation is the project's own — around 70 lines in
`src/i18n/I18nProvider/I18nProvider.tsx` — with no i18n library involved.

- `AVAILABLE_LANGUAGES` lists the supported locales; `translations` maps each to
  its imported JSON. **Spanish is the only language today**, and the locale
  starts as `es`.
- `t(key)` splits the key on `.` and walks the dictionary. **If the path does not
  resolve to a string it returns the key itself**, so a missing translation
  shows up as `home.call-to-action` on the page rather than as a blank or a
  crash. Seeing a dotted key in the interface means a key is missing or
  misspelt.
- `t(key, params)` substitutes `{{name}}` placeholders:
  `t("recipes.count", { count: 3 })` against `"{{count}} recetas"`.
- `setLocale` ignores any value not in `AVAILABLE_LANGUAGES`, so an unknown
  locale leaves the current one alone.

## Translation files

One JSON file per language in `src/i18n/locales/`, named by locale code —
`es.json` today.

```json
{
  "app": {
    "name": "Muncher",
    "slogan": "Comer sano no tiene que ser aburrido"
  },
  "authentication": {
    "log-in": "Iniciar sesión"
  }
}
```

- **Keys are nested one level deep**, grouped by area: `app`, `authentication`,
  `footer`, `home`. The group is the feature or the screen, not the component.
- **Key segments are `kebab-case`** (`log-in`, `call-to-action`).
- **Groups and keys are ordered alphabetically.** Keep them that way: it makes a
  missing key easy to spot and keeps diffs small.
- **Keys are named for meaning, not for the text.** `home.call-to-action`, not
  `home.empezar` — the Spanish wording can change without touching a component.
- **Values are Spanish**, and written per [tone.md](../memoria/tone.md)'s rule on
  untranslated technical terms where one applies.

## Adding a string

1. Add the key to `src/i18n/locales/es.json`, in the right group, in
   alphabetical order. Create the group if the area is new.
2. Call `t("group.key")` in the component.
3. If a language is ever added, add its file to `locales/`, its code to
   `AVAILABLE_LANGUAGES` and its import to `translations`. All three are
   required — a file alone does nothing.

## What to watch for

- **A dotted key rendering on screen** means `t()` could not resolve it: check
  for a typo, or that the key exists in the locale file.
- **No check enforces this.** Nothing in the pipeline fails when a component
  hardcodes a string or when a key is missing, so it rests on review. The hero
  had exactly that defect — the mobile layout rendered `Empezar` literally while
  the desktop one used `t("home.call-to-action")` for the same button — and it
  went unnoticed because both layouts render the same word.
- **Spell checking covers the Spanish text.** `cspell` runs with the `es-es`
  dictionary, so a misspelt translation fails the checks; add genuine project
  words to `front-end/cspell-project-words.txt` rather than disabling the rule.
